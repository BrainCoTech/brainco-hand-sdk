# Revo2 CAN FD 报文解析说明

本文定义配套脚本使用的 Revo2 应用层报文：读取 SN、固件版本、左右手信息、马达状态，以及六通道百分比位置控制。适用于本文所列寄存器和功能码，不是 CAN 2.0、OTA 或所有设备寄存器的完整协议手册。

文中从站为 126 / `0x7E`、127 / `0x7F`，主站为 1 / `0x01`。从站地址不决定左右手，左右手由 SKU 寄存器返回值判断。下文未标注十六进制的寄存器地址均为十进制；字节偏移均从 0 开始。

## 1. 总线与 CAN ID

使用 29 位扩展帧、CAN FD、BRS 开启。配套测试配置为：仲裁域 1 Mbps、75% 采样点；数据域 5 Mbps、75% 采样点。控制器收到的实际设置以 `ip -details -statistics link show dev can0` 为准。

```text
CAN ID = (slave_id << 16) | (master_id << 8) | logical_length
```

| CAN ID 位段 | 定义 |
| --- | --- |
| bit 28～24 | 保留，本文报文为 0 |
| bit 23～16 | 从站 ID，8 位 |
| bit 15～8 | 主站 ID，8 位 |
| bit 7～0 | 应用层有效长度，单位：字节，包含末尾两个 CRC16 字节，不含补齐字节 |

请求和应答使用相同的主从字段，应答不交换主从位置。请求和应答长度可以不同，因此完整 CAN ID 通常不同。

例如 `0x007F011D`：从站 `0x7F=127`，主站 `0x01=1`，应用层有效长度 `0x1D=29` 字节。

SocketCAN 的 `CAN_EFF_FLAG` 是 API 层表示扩展帧的标志，不属于上述 29 位 ID。`candump` 的扩展 ID 可能显示为 `007F011D`；ZCANPro 等工具可能用后缀或另一列表示扩展帧。

## 2. 字节序、有效长度与补齐

- 寄存器地址、寄存器数量和 16 位寄存器数据：高字节在前，大端。
- 应用层 CRC16：低字节在前，小端。
- ASCII 字符串：按返回数据的字节顺序拼接，去掉尾部 `00`；不要交换每对字符。
- CAN ID 的低 8 位给出应用层有效长度。控制器报告的 CAN FD 数据长度可能更大，额外字节为补齐区，不参与应用层 CRC16。

CAN FD 的物理数据字节数可为 0～8、12、16、20、24、32、48、64。逻辑长度 29 字节可以装在 32 字节帧中，也可能装在更长的 48 或 64 字节帧中；接收端不能假定总是最小补齐长度。

| 读寄存器数量 | 应用层有效长度 | CRC 输入字节数 | CRC 偏移 | 常见最小物理长度 |
| --- | --- | --- | --- | --- |
| 1 | 7 | 5 | 5、6 | 7 |
| 10 | 25 | 23 | 23、24 | 32 |
| 12 | 29 | 27 | 27、28 | 32 |
| 24 | 53 | 51 | 51、52 | 64 |
| 29 | 63 | 61 | 61、62 | 64 |

DLC 编码值和物理字节数不是同一个量。以 SocketCAN `canfd_frame.len` 为例，它表示实际字节数；抓包软件若同时导出 DLC 和长度，应看清各列定义。

## 3. 读请求：功能码 0x03 / 0x04

`0x03` 用于本文 SKU 保持寄存器；`0x04` 用于 SN、固件及马达输入寄存器。

| 字节偏移 | 长度 | 含义 |
| --- | --- | --- |
| 0 | 1 | 从站 ID |
| 1 | 1 | 功能码 `03` 或 `04` |
| 2～3 | 2 | 起始寄存器地址，大端 |
| 4～5 | 2 | 寄存器数量 N，大端 |
| 6 | 1 | CRC16 低字节 |
| 7 | 1 | CRC16 高字节 |

读请求有效长度固定为 8 字节，CRC 输入为偏移 0～5。

读取 127 的当前位置和速度，2000 起共 12 个寄存器：

```text
TX CAN ID: 007F0108
TX DATA:   7F 04 07 D0 00 0C FA 9C
           |  |  ----- ----- -----
           |  |  2000  12    CRC=0x9CFA，低字节 FA 先发
           |  功能码 04
           从站 127
```

## 4. 正常读应答

| 字节偏移 | 长度 | 含义 |
| --- | --- | --- |
| 0 | 1 | 从站 ID |
| 1 | 1 | 与请求相同的功能码 |
| 2 | 1 | 数据字节数，正常应为 `2 × N` |
| 3 起 | `2 × N` | 寄存器数据，每个寄存器 2 字节，大端 |
| `3 + 2 × N` | 1 | CRC16 低字节 |
| `4 + 2 × N` | 1 | CRC16 高字节 |
| 有效长度后 | 可选 | CAN FD 补齐字节，通常为 `00` |

应答有效长度为 `5 + 2 × N`。读取 N 个寄存器时，要同时检查从站、主站、功能码、byte_count、有效长度、实际接收长度和 CRC，不能仅凭 CAN ID 主从字段接受一帧。

正常读应答不回显起始寄存器地址。相同从站、相同功能码、相同数量的不同地址读操作，其应答 CAN ID 和长度可以相同。因此保持一问一答，避免多个线程或程序同时发请求；遇到超时还需考虑延迟应答。

上述 12 寄存器请求的一条构造示例应答，所有寄存器值取 0：

```text
RX CAN ID: 007F011D
RX DATA:   7F 04 18 00 00 00 00 00 00 00 00 00 00 00 00 00
           00 00 00 00 00 00 00 00 00 00 00 83 9D 00 00 00
```

本例实际长度 32 字节，有效长度 29 字节，偏移 27、28 为 `83 9D`，即 CRC16 `0x9D83`。最后 3 字节是补齐，不参与计算。这是协议构造示例，不是实机状态记录。

## 5. 读取项目与数据定义

| 项目 | 功能码 | 起始地址（十进制 / 十六进制） | 数量 | 解析 |
| --- | --- | --- | --- | --- |
| SN | `04` | 3010 / `0BC2` | 10 | 20 字节 ASCII，去尾部 `00` |
| 固件版本 | `04` | 3000 / `0BB8` | 10 | 20 字节 ASCII，去尾部 `00` |
| 左右手 SKU | `03` | 901 / `0385` | 1 | 1、3 为右手；2、4 为左手；其他保留原值 |
| 位置与速度 | `04` | 2000 / `07D0` | 12 | 前 6 个位置，后 6 个速度 |
| 电流与马达状态 | `04` | 2012 / `07DC` | 12 | 前 6 个电流，后 6 个状态 |
| 完整马达状态 | `04` | 2000 / `07D0` | 24 | 依次为 6 位置、6 速度、6 电流、6 状态 |

六通道顺序沿用协议定义：`Thumb`、`ThumbAux`、`Index`、`Middle`、`Ring`、`Pinky`。每组通道对应连续 6 个寄存器：

| 地址范围 | 内容 | 数值解释 |
| --- | --- | --- |
| 2000～2005 | 位置 | 无符号 16 位原始值 |
| 2006～2011 | 速度 | 有符号 16 位，二进制补码 |
| 2012～2017 | 电流 | 有符号 16 位，二进制补码 |
| 2018～2023 | 马达状态 | 每通道一个寄存器，状态值见下表 |

| 马达状态值 | SDK 定义 |
| --- | --- |
| 0 | `Idle`，空闲 |
| 1 | `Running`，运行 |
| 2 | `Stall`，堵转 |
| 3 | `Turbo` |
| 255 | `Unknown` |

未列出的值保留原始值，不猜测含义。原始位置、速度和电流的单位、比例与设备模式和固件定义有关；不能仅凭本表把原始值统一当作角度或毫安。直接收发版保留原始寄存器值，SDK 版按其 API 返回解析结果，比较时先核对单位和缩放。

读取 127 的 SN 请求和应答格式：

```text
TX CAN ID: 007F0108
TX DATA:   7F 04 0B C2 00 0A D9 CB
RX CAN ID: 007F0119
RX BODY:   7F 04 14 [20 字节 SN 数据] CRC_LO CRC_HI [补齐]
```

对应 126 的请求 CRC 不同，不能只将上述 `7F` 改为 `7E` 而沿用原 CRC。两地址的完整请求和示例应答见 [frame_reference.txt](direct/frame_reference.txt)。

## 6. 张合控制：0x10 写多个寄存器

配套脚本向 1070～1072 写入六通道百分比位置，范围 0～100。每两个通道打包为一个 16 位寄存器：

```text
word0 = (ThumbAux << 8) | Thumb
word1 = (Middle   << 8) | Index
word2 = (Pinky    << 8) | Ring
```

每个 word 按大端发送，所以线路上的两个字节是“后一通道、前一通道”。该特殊打包规则仅针对这里的百分比位置寄存器，不应套用到普通状态寄存器。

### 写请求

| 字节偏移 | 长度 | 含义 |
| --- | --- | --- |
| 0 | 1 | 从站 ID |
| 1 | 1 | 功能码 `10` |
| 2～3 | 2 | 起始地址 `04 2E`，即 1070 |
| 4～5 | 2 | 寄存器数量 `00 03` |
| 6 | 1 | 数据字节数 `06` |
| 7～12 | 6 | 3 个寄存器数据，大端 |
| 13、14 | 2 | CRC16，低字节先发 |
| 15 起 | 可选 | CAN FD 补齐 |

写请求有效长度为 15 字节，常用物理长度 16 字节。一般 0x10 请求写 N 个寄存器，有效长度为 `9 + 2 × N`；单帧最多写 27 个寄存器。正常读应答单帧最多返回 29 个寄存器，读写上限不同。

### 写应答

正常应答回显请求的前 6 字节，再跟随 2 字节 CRC：

```text
slave 10 address_hi address_lo count_hi count_lo CRC_LO CRC_HI
```

写应答有效长度固定为 8 字节。不能把写应答的地址高字节当成读应答的 byte_count。正确回显不代表运动已完成，应继续读取马达状态和位置。

### 127 的张合示例

张开六通道百分比均为 0：

```text
TX CAN ID: 007F010F
TX DATA:   7F 10 04 2E 00 03 06 00 00 00 00 00 00 3A 91 00
RX CAN ID: 007F0108
RX DATA:   7F 10 04 2E 00 03 EB 2F
```

闭合测试目标为 `[50, 50, 100, 100, 100, 100]`：

```text
TX CAN ID: 007F010F
TX DATA:   7F 10 04 2E 00 03 06 32 32 64 64 64 64 72 83 00
RX CAN ID: 007F0108
RX DATA:   7F 10 04 2E 00 03 EB 2F
```

这两条写请求有效数据分别以 `3A 91`、`72 83` 结束，最后一个 `00` 均为补齐。写应答只回显地址和数量，因此这两条命令的正常写应答相同。以上应答为按协议计算的期望格式，不是真机动作验证记录。

这些请求会引发手指运动；仅在明确需要动作且周围无遮挡时发送。脚本默认只读，不自动循环张合。

## 7. 异常应答

设备返回 Modbus 异常时，功能码是原请求功能码或上 `0x80`，例如 `04` 对应 `84`、`10` 对应 `90`：

```text
slave (function | 80) exception_code CRC_LO CRC_HI
```

异常应答有效长度为 5 字节，CRC 输入为前 3 字节。保留原始异常码，并按设备协议解释；它不是普通读应答的 byte_count。

超时表示未收到匹配应答；应答头不匹配、长度错误、CRC 错误和异常码是不同现象，应分别记录。CAN 控制器的错误帧也不是这种应用层异常应答，需结合接口错误计数和原始抓包单独排查。

## 8. CRC16 计算与接收检查

CRC16 参数：Modbus CRC16，初始值 `0xFFFF`，反向多项式 `0xA001`，结果不再异或，发送时低字节在前。输入包括从站、功能码及报文中的其余有效字段，但不包括 CAN ID、FD/BRS 标志、DLC、CRC 字节自身或末尾补齐。

```python
def crc16_modbus(data):
    crc = 0xFFFF
    for byte in data:
        crc ^= byte
        for _ in range(8):
            crc = (crc >> 1) ^ (0xA001 if crc & 1 else 0)
    return crc


assert crc16_modbus(b"123456789") == 0x4B37
```

接收时先检查缓冲区边界，再取 CRC：

1. 确认是目标 CAN FD 扩展数据帧，核对 CAN ID 中的主从字段。
2. 从 CAN ID 取有效长度 L，要求 `L <= 实际收到字节数 <= 64`，且 L 至少容纳该报文的头和 CRC。
3. 核对数据区从站 ID、功能码和报文格式。普通读应答检查 byte_count 为偶数且等于请求数量的两倍，并要求 `L = 5 + byte_count`；写应答检查 `L = 8` 且前 6 字节匹配请求；异常应答检查 `L = 5`。
4. 仅对 `data[0:L-2]` 计算 CRC，取 `data[L-2] | (data[L-1] << 8)` 比较。使用从 0 开始的下标。
5. 将 `data[L:]` 单独记录为补齐，不放入 CRC 输入；CRC 正确后再按寄存器或字符串解释数据。

本节讨论应用层 CRC16。CAN FD 控制器自身处理的链路层 CRC 是另一层校验；能收到 CAN 帧，并不自动证明应用层 CRC16 正确。
